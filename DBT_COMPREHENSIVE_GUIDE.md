## Project Overview

This is a **dbt (Data Build Tool)** project named **walmart_T3** that transforms raw data from a PostgreSQL/Fabric database into clean, structured data models. dbt is a command-line tool that enables data engineers to transform data in their database using SQL and Python, similar to how software engineers use version control and testing.

**Key Information:**
- **Project Name:** walmart_T3
- **Version:** 1.0.0
- **Database:** Azure Fabric (Microsoft Data Warehouse)
- **Source Database:** Postgres_LH
- **Schema:** dbo (Database Objects)
- **Authentication Method:** Service Principal (Azure AD)

#### Lines 10-18: Path Configuration Comments and Model/Resource Paths
```yaml

# found in the "models/" directory. You probably won't need to change these!

analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]
```

**What Each Path Does:**

| Path Key | Directory | Purpose |
|----------|-----------|---------|
| `model-paths` | `models/` | Contains SQL/Python files that define transformations. These become tables or views in your database |
| `analysis-paths` | `analyses/` | Contains SQL files for analysis that WON'T be materialized as tables. Used for exploratory queries |
| `test-paths` | `tests/` | Contains data validation tests (e.g., checking for NULL values, uniqueness) |
| `seed-paths` | `seeds/` | Contains CSV files that get loaded into your database as tables |
| `macro-paths` | `macros/` | Contains reusable SQL/Jinja templates that can be called from multiple models |
| `snapshot-paths` | `snapshots/` | Contains snapshot configurations to track historical changes in data |

**Current Configuration:** 
- All paths use defaults, which is standard for most projects
- Models will be searched in `walmart_T3/models/`
- Tests will be searched in `walmart_T3/tests/`
- And so on...

#### Lines 20-22: Clean Targets
```yaml
clean-targets:         # directories to be removed by `dbt clean`
  - "target"
  - "dbt_packages"
```
- **Purpose:** Specifies which directories get deleted when running `dbt clean`
- **When Used:** `dbt clean` removes build artifacts to start fresh
- **target:** Contains compiled SQL and manifest files generated by dbt
- **dbt_packages:** Contains downloaded dependencies from packages
- **Safety:** These are build artifacts that can be safely deleted

#### Lines 25-30: Model Configuration
```yaml
# Configuring models
# Full documentation: https://docs.getdbt.com/docs/configuring-models
models:
  walmart_T3:
    staging:
      +materialized: view
```

**Breaking This Down:**

- **`models:`** - Section that configures how models behave
- **`walmart_T3:`** - Project-level configuration (applies to all models in this project)
- **`staging:`** - Folder-level configuration (applies only to models in `models/staging/`)
- **`+materialized: view`** - Configuration setting
  - **`materialized`:** How the model is created in the database
  - **`view`:** Creates a SQL VIEW (virtual table, recalculated on each query)
  - **`+` prefix:** Means "apply to this level and all children"

**Materialization Options:**
- `view` - Virtual table, queries the source SQL every time (smaller storage, slower queries)
- `table` - Physical table, stored on disk (larger storage, faster queries)
- `incremental` - Updates existing table with only new rows (best for large datasets)
- `ephemeral` - Temporary, only exists during dbt run (not materialized in database)
- `dynamic_table` - Azure Fabric specific, materialized view with auto-refresh

**In Your Project:** All models in `staging` folder will be created as views by default.

### 5. `stg_customers.sql` - Staging Model

```sql
select * from {{ source('bronze', 'bronze_customers') }}
```

**Line-by-Line Breakdown:**

| Part | Explanation |
|------|-------------|
| `select *` | SQL statement selecting ALL columns |
| `from` | SQL keyword indicating the data source |
| `{{ source('bronze', 'bronze_customers') }}` | Jinja templating syntax |

**The Jinja Part Explained:**
```
{{ source('bronze', 'bronze_customers') }}
```
- **`{{ ... }}`:** Jinja template expression (dbt executes this)
- **`source()`:** dbt function that references a defined source
- **`'bronze'`:** First argument - the source name (from sources.yml)
- **`'bronze_customers'`:** Second argument - the table name (from sources.yml)

**What dbt Does:**
1. When you run `dbt run`, dbt reads sources.yml
2. It finds the bronze source pointing to Postgres_LH.dbo.bronze_customers
3. It replaces `{{ source('bronze', 'bronze_customers') }}` with the actual table reference
4. Final SQL sent to database:
   ```sql
   select * from [Postgres_LH].[dbo].[bronze_customers]
   ```

**Model Behavior:**
- **Name:** Model file name (stg_customers) becomes the table/view name
- **Materialization:** Uses `view` (from dbt_project.yml `staging` section)
- **Output:** Creates or replaces a view called `stg_customers` in your database
- **Purpose:** "stg_" prefix indicates this is a staging model (intermediate, not final)

**Staging Layer Concept:**
- **Bronze (Raw):** Original data from sources (bronze_customers)
- **Silver (Staging):** Cleaned, standardized data (stg_customers)
- **Gold (Analytics):** Final, business-ready data (customers)

## dbt Concepts Explained

### 1. Models

**What They Are:** SQL files that define data transformations

**In Your Project:**
- `stg_customers.sql` is a model
- Creates a view named `stg_customers` in your database

**Types:**
- **Views:** Virtual tables, no storage, recalculated on query
- **Tables:** Physical tables, stored on disk
- **Ephemeral:** Temporary, used by other models only
- **Incremental:** Large tables that only insert new rows
- **Materialized Views:** Auto-refreshing views (Azure Fabric)

**Lifecycle:**
1. Write SQL in model file
2. Reference other models using `{{ ref() }}` or `{{ source() }}`
3. Run `dbt run` to execute
4. dbt creates/updates the object in your database

### 2. Sources

**What They Are:** Metadata about external tables (raw data)

**In Your Project:**
- `sources.yml` defines 6 sources from the bronze layer
- Each source points to a real table in Postgres_LH.dbo

**Why Use Them:**
- Document where data comes from
- Create lineage (dependency graphs)
- Test data quality before models use it
- Central place to change table references

**Without Sources:**
```sql
-- ❌ Hard to track, hard to refactor
select * from Postgres_LH.dbo.bronze_customers
```

**With Sources:**
```sql
-- ✅ Clear, trackable, easy to refactor
select * from {{ source('bronze', 'bronze_customers') }}
```

### 3. Profiles

**What They Are:** Database connection configurations

**In Your Project:**
- `profiles.yml` defines how to connect to Azure Fabric
- `dbt_project.yml` references the `walmart_fabric` profile
- Contains authentication details (tenant, client ID, secret)

**Production Pattern:**
```yaml
# profiles.yml
client_secret: "{{ env_var('DBT_FABRIC_CLIENT_SECRET') }}"

# Command line
export DBT_FABRIC_CLIENT_SECRET="actual-secret"
dbt run --profile walmart_fabric --target fabric
```

### 4. Jinja Templating

**What It Is:** Template syntax that dbt processes before sending SQL to database

**In Your Project:**
```sql
{{ source('bronze', 'bronze_customers') }}
```

**Common Jinja Functions:**
| Function | Purpose | Example |
|----------|---------|---------|
| `{{ ref() }}` | Reference another model | `{{ ref('stg_customers') }}` |
| `{{ source() }}` | Reference a source table | `{{ source('bronze', 'bronze_customers') }}` |
| `{{ env_var() }}` | Get environment variable | `{{ env_var('MY_VAR') }}` |
| `{{ config() }}` | Configure model behavior | `{{ config(materialized='table') }}` |

### 5. Run Results

**What Happens During `dbt run`:**

```
dbt run
├── Parse: Read all YAML files and SQL models
├── Construct: Build dependency graph
├── Execute: Run SQL in dependency order
│   └── Compile stg_customers.sql
│       └── Replace {{ source(...) }} with actual table name
│       └── Execute: CREATE VIEW stg_customers AS SELECT * FROM [Postgres_LH].[dbo].[bronze_customers]
└── Report: Show results (success/error)
```

## Best Practices to Follow

### 1. **Naming Conventions**
- Models: lowercase with underscores (`stg_customers`, `dim_products`)
- Sources: clearly indicate layer (`bronze_`, `silver_`)
- Database objects: use prefixes for clarity

### 2. **Model Organization**
- **staging/:** Clean and standardize raw data
- **intermediate/:** Join and combine staging models
- **marts/:** Final, business-ready models
  - **marts/core/:** Essential dimensions and facts
  - **marts/finance/:** Finance-specific models
  - **marts/marketing/:** Marketing-specific models

## Troubleshooting Guide

### Problem: "Could not load connection"
**Cause:** profiles.yml not found or profile name mismatch
**Solution:**
```bash
# Check profiles location
dbt debug

# Ensure profile in dbt_project.yml matches profiles.yml
# profile: 'walmart_fabric'  ← Must exist in profiles.yml
```

### Problem: "Profile not found"
**Cause:** profiles.yml doesn't have the referenced profile
**Solution:**
```bash
# Fix: Ensure profiles.yml has:
walmart_fabric:
  target: fabric
  outputs:
    fabric:
      ...
```

### Problem: "Authentication failed"
**Cause:** Invalid credentials or expired token
**Solution:**
```bash
# Check credentials
cat ~/.dbt/profiles.yml

# Verify Azure credentials
az account show

# Refresh token
az login
```

### Problem: "Table not found"
**Cause:** Source table doesn't exist in database
**Solution:**
```sql
-- Verify table exists:
SELECT * FROM Postgres_LH.dbo.bronze_customers LIMIT 1

-- Check schema:
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES 
WHERE TABLE_SCHEMA = 'dbo' AND TABLE_NAME LIKE 'bronze%'
```
